When UAT is enabled, `superagent check` runs user acceptance tests before the Claude Code review, and the waiting marker is still `Waiting for checks: PR #<number> at <sha>`. `uat-test` is the independent tester inside that command: never run the tester another way, never state UAT results you did not get from a check, never post a UAT result yourself, never edit, add or remove an issue's `## User Acceptance Tests` section, and never change a test's expected outcome to make it pass.
Check exit codes (`superagent check` / `superagent merge`): `0` pass · `1` fail · `2` blocked · `3` retry · `4` precondition. Last line: `superagent: <VERDICT> for <sha>`. Compact lines include `superagent: next <step>`. On exit `1`, read the detail file named in the output; otherwise act on the exit status and the `next` line alone. `uat-test --artifact <run id> <path>` prints a file a UAT run kept, such as `app-logs/app.log`, `setup.log` or the evidence under `tester-work/attempt-1/screens/`.
Follow the Check exit codes table and `next:` from Delivery:
- Exit status `0` with `next done` is a pass, or no UAT for this issue, for exactly <sha>: continue to merge. `next run superagent check` means the review is still due: run `superagent check` again for the same head. Never merge a head whose check did not reach `next done`.
- `1` is a fail: read the detail file, fix the application so that every failing scenario behaves as the issue expects, run what reproduces it, push and review the new head. A report that says the PR cannot be tested (no `Closes #<n>` line, or none for the issue this ticket started from, `.superagent/uat.yaml` missing or invalid, the setup or start command failing) is fixed in the PR the same way. The gate names this ticket's issue from `DSH_SUPERAGENT_GITHUB_NUMBER`.
- A scenario the report says could not be run is a fail too: make it runnable in the PR, from what the tester says is missing, without changing what the scenario checks. A fixture or record the steps need comes from `.superagent/uat.yaml`'s setup or start command; a control the steps need that the tester lacks (such as restarting the server) is provided by the start command, for example a supervisor that restarts the application on a request to another 127.0.0.1 port, and documented in the repository, where the tester reads how to call the application. Only when the issue alone could make it runnable (an ambiguous step, a step asking for something other than exercising the application) report blocked with the report's reasons and never merge.
- `2` is blocked (the issue's UAT section is invalid, the environment is not allowed, the runner is unavailable, the tester's answer could not be trusted, the PR used up its three failing UAT rounds, or three failed reviews): report blocked with the report's reasons and never merge. Run `superagent check` once more for the same <sha> only when the report names the runner or the gate; otherwise, or if it is blocked again, stop.
- `3` is retry (no verdict: gate unreachable, timeout, a result that does not match the head or spec, or a report that could not be posted): run `superagent check` once more for the same <sha>, and if that is not `0`, `1` or `2` either, report blocked with its message.
Every new commit is a new head, whatever its reason (a UAT fix, a review's fix plan, a rebase, a co-author trailer): earlier results no longer count, and the new head gets `superagent check` again. A PR gets at most three failing UAT rounds, counted by the gate across heads and restarts, separately from its three failed reviews (counted from stored reviews by `superagent check`).
Merge with `superagent merge` as in Delivery and follow `next:`. When merge names a UAT precondition, run `superagent check` for that head again and continue from its result. UAT is not a GitHub check: do not wait for or require a `superagent/uat` check.
