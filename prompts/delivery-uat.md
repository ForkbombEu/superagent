User acceptance tests (UAT) run on every PR head you push, before its Claude Code review. `uat-test` is the independent tester, as `claude-review` is the independent reviewer, and is the only way you run UAT: it asks the deployment's UAT gate to run the issue's scenarios against exactly <sha> with a DeepSeek tester that is not you, and its exit status is the verdict. Never run the tester another way, never state UAT results you did not get from `uat-test`, never post a UAT result yourself, never edit, add or remove an issue's `## User Acceptance Tests` section, and never change a test's expected outcome to make it pass.
In "Review the PR's current head", between steps 1 and 2: in the ticket directory, run `uat-test $DSH_SUPERAGENT_GITHUB_REPOSITORY <number> <sha>` as a background job and end your turn; its end wakes you with its output. It waits for the verdict on <sha>, posts the report on the PR as the record of the run and prints it: the verdict, each failing scenario with what was expected, what was observed and how to reproduce it, and the UAT run id. Its output ends with the path of a file holding the whole report and a last line `uat-test: PASS|NOT_REQUIRED|FAIL|BLOCKED for <sha>`; read that whole file. `uat-test --artifact <run id> <path>` prints a file the run kept, such as `app-logs/app.log`, `setup.log` or the evidence under `tester-work/attempt-1/artifacts/`.
- Exit status 0 is a pass, or no UAT for this issue, for exactly <sha>: continue with step 2 for the same <sha>. Never run `claude-review` on a head whose `uat-test` did not exit 0; `claude-review` itself refuses with exit status 4 when UAT has not passed for its <sha>, and then you run `uat-test` for that <sha> first.
- 1 is a fail: fix the application so that every failing scenario behaves as the issue expects, run what reproduces it, push and review the new head from step 1. A report that says the PR cannot be tested (no `Closes #<n>` line, `.superagent/uat.yaml` missing or invalid, the setup or start command failing) is fixed in the PR the same way.
- 2 is blocked (a scenario could not be run, the issue's UAT section is invalid, the environment is not allowed, the runner is unavailable, or the PR used up its three failing UAT rounds): run it once more for the same <sha> when the report names the runner or the gate; otherwise, or if it is blocked again, report blocked with the report's reasons and never merge.
- Any other status is no verdict: run it once more for the same <sha>, and if that is not 0, 1 or 2 either, report blocked with its message.
Every new commit is a new head, whatever its reason (a UAT fix, a review's fix plan, a rebase, a co-author trailer): both earlier results no longer count, and the new head gets `uat-test` and then `claude-review` again, in that order. A PR gets at most three failing UAT rounds, counted by the gate across heads and restarts, separately from its three failed reviews. Record each UAT <sha>, run id and result in orchestrator_report.
Merging needs, for the PR's current head and title read again right before merging: a UAT pass or NOT_REQUIRED for that head that still holds, checked by running `uat-test --verify $DSH_SUPERAGENT_GITHUB_REPOSITORY <number> <reviewed sha>` and merging only when it exits 0; a passing Claude Code review of that head and title; every required check passed; no review requesting changes; and then the merge command above. When `uat-test --verify` exits 1 (the issue's UAT or the environment changed since the pass), run `uat-test` for that head again and continue from its result. UAT is not a GitHub check: do not wait for or require a `superagent/uat` check.
